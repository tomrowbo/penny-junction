# Banking AI architecture and privacy

## What authoritative sources recommend for LLM access to structured financial data

### Takeaway
Authoritative sources do not support treating an LLM prompt as the security boundary. The defensible pattern is a conventional authenticated application layer between the model and data, with least-privilege tools, database-enforced customer scoping, read-only access, parameterisation/validation, and bounded execution.

### Cited Findings
- OWASP says prompt injection cannot be eliminated architecturally and identifies privilege minimisation as the most effective control; for agents it recommends permission and parameter validation at the tool boundary, read-only database accounts where possible, minimal API scopes, monitoring, and human confirmation for consequential actions. — [OWASP Prompt Injection](https://genai.owasp.org/glossary/prompt-injection/); [OWASP LLM Prompt Injection Prevention Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/LLM_Prompt_Injection_Prevention_Cheat_Sheet.html)
- OWASP specifically says critical controls such as privilege separation and authorisation bounds must be enforced outside the LLM in a deterministic, auditable manner. — [OWASP System Prompt Leakage guidance](https://genai.owasp.org/llmrisk/llm072025-system-prompt-leakage/)
- AWS's reference implementation for a database-connected Bedrock agent separates query generation from execution, validates generated SQL against allowed operations and syntax, uses a database role with read-only permissions, and recommends production use only for read-only analytics/reporting because model-generated writes create data-integrity and security risk. — [AWS database architecture](https://aws.amazon.com/blogs/database/connect-amazon-bedrock-agents-with-amazon-aurora-postgresql-using-amazon-rds-data-api/)
- A second AWS text-to-SQL reference uses parameterised SQL and a role limited to `SELECT`; it explains that parameters keep user input separate from SQL syntax and that the restricted role provides another security layer. — [AWS text-to-SQL best practices](https://aws.amazon.com/blogs/database/build-an-ai-powered-text-to-sql-chatbot-using-amazon-bedrock-amazon-memoryDB-and-amazon-rds/)
- Google Cloud's QueryData documentation recommends parameterised secure views that bind authenticated-user parameters to enforce strict row-level security and protect against prompt injection. — [Google Cloud QueryData](https://docs.cloud.google.com/gemini/data-agents/querydata)
- PostgreSQL row-level security can restrict which rows each user can return; once enabled, access must pass a policy and absence of an applicable policy produces default deny. PostgreSQL also supports read-only transactions that disallow data-changing and schema-changing SQL, plus statement timeouts that abort overlong queries. — [PostgreSQL row security](https://www.postgresql.org/docs/current/ddl-rowsecurity.html); [PostgreSQL read-only transactions](https://www.postgresql.org/docs/17/sql-set-transaction.html); [PostgreSQL statement timeout](https://www.postgresql.org/docs/19/runtime-config-client.html)

### Inferences
- For Penny, an allowlisted analytics-tool interface (`spend_by_category`, `cashflow_summary`, `safe_to_spend`, `simulate_reduction`) is safer and easier to validate than arbitrary text-to-SQL. The LLM can choose a tool and bounded parameters, while bank code owns SQL, basket classification, and arithmetic. This is an architectural inference from OWASP's tool-boundary guidance and the layered controls in the AWS/Google references, not evidence that all banks implement the same design. — [OWASP tool boundary guidance](https://cheatsheetseries.owasp.org/cheatsheets/LLM_Prompt_Injection_Prevention_Cheat_Sheet.html); [AWS database architecture](https://aws.amazon.com/blogs/database/connect-amazon-bedrock-agents-with-amazon-aurora-postgresql-using-amazon-rds-data-api/); [Google Cloud QueryData](https://docs.cloud.google.com/gemini/data-agents/querydata)
- If free-form SQL is needed for a demo, customer scoping should be injected from the authenticated server session and enforced by row-level security or a parameterised secure view, never supplied or trusted from model output. Execution should additionally use a non-owner read-only role, single-statement `SELECT` allowlisting, time/row limits, and an audit record. This combines documented controls rather than claiming one source mandates the full stack. — [PostgreSQL row security](https://www.postgresql.org/docs/current/ddl-rowsecurity.html); [AWS database architecture](https://aws.amazon.com/blogs/database/connect-amazon-bedrock-agents-with-amazon-aurora-postgresql-using-amazon-rds-data-api/); [Google Cloud QueryData](https://docs.cloud.google.com/gemini/data-agents/querydata)

### Gaps
- Public sources do not establish a single universal architecture used by “serious banks”; individual banks generally do not disclose their production database permissions, row-level policies, or model context construction in sufficient detail.
- The cited AWS and Google designs are vendor reference architectures, not proof that a named bank uses them.

## Whether aggregates and pseudonymised financial facts remain personal data under GDPR

### Takeaway
Removing names and account numbers reduces risk but ordinarily does not make a per-customer financial analysis anonymous. If facts are generated for a logged-in customer's conversation or can be attributed using additional information, they remain personal data and GDPR still applies.

### Cited Findings
- The EDPB states that pseudonymised data which can be attributed to a natural person using additional information remains personal data; this is true even when the pseudonymised data and additional information are held by different parties, if they can reasonably be combined. — [EDPB Guidelines 01/2025 on Pseudonymisation](https://www.edpb.europa.eu/system/files/2025-01/edpb_guidelines_202501_pseudonymisation_en.pdf)
- The EDPB distinguishes pseudonymisation from anonymisation: only truly anonymised, unlinkable data falls outside EU data protection law. Its practical guidance uses singling out, linkability, and inference as the three tests for effective anonymisation. — [EDPB anonymisation and pseudonymisation topic](https://www.edpb.europa.eu/topics/ai-and-technology/anonymisation-pseudonymisation_en); [EDPB personal-data security guide](https://www.edpb.europa.eu/sme/be-compliant/secure-personal-data_en)
- GDPR Article 5 requires personal data to be adequate, relevant, and limited to what is necessary for the purpose, while Article 25 requires data protection by design and default and identifies pseudonymisation and data minimisation as possible safeguards. — [GDPR Article 5](https://eur-lex.europa.eu/eli/reg/2016/679/oj/eng/); [GDPR Article 25](https://eur-lex.europa.eu/legal-content/EN/TXT/PDF/?uri=CONSIL%3APE_17_2016_INIT)
- The EDPB's Opinion 28/2024 says whether an AI model is anonymous requires a case-by-case assessment and evidence that personal data cannot be extracted and that model outputs do not relate to the people whose data trained the model. It also identifies filtering, output controls, pseudonymisation/anonymisation consideration, and data-minimisation strategies as relevant safeguards. — [EDPB Opinion 28/2024](https://www.edpb.europa.eu/documents/opinion-of-the-board-art-64/opinion-282024-on-certain-data-protection-aspects-related-to_en)

### Inferences
- A value such as “your safe-to-spend amount is €437” is personal data when returned inside an authenticated customer's session because it directly relates to that customer, even if their name and IBAN are omitted from the model prompt. Therefore “no PII is sent” is not a safe legal or technical claim; “no direct identifiers or raw transaction records are sent, and customer-derived facts are minimised” is more accurate. This conclusion applies the EDPB's attribution/linkability standard to the Penny flow. — [EDPB Guidelines 01/2025](https://www.edpb.europa.eu/system/files/2025-01/edpb_guidelines_202501_pseudonymisation_en.pdf); [GDPR](https://eur-lex.europa.eu/eli/reg/2016/679/oj/eng/)
- If S-Bank requires that no customer personal data leave its controlled environment, data minimisation alone is insufficient: the model inference endpoint and its processing/logging must also remain within an approved bank-controlled or contractually governed environment. — [EDPB Guidelines 01/2025](https://www.edpb.europa.eu/system/files/2025-01/edpb_guidelines_202501_pseudonymisation_en.pdf); [DORA Article 28](https://eur-lex.europa.eu/legal-content/EN/TXT/?uri=CELEX%3A32022R2554)

### Gaps
- Whether a particular aggregate is anonymous depends on the complete deployment context, recipient capabilities, other available data, session linkability, retention, and contractual/technical controls; no generic field list can establish anonymity.
- This note does not determine S-Bank's lawful basis, controller/processor roles, international-transfer mechanism, or DPIA requirements; those require the real provider contract and deployment details.

## Patterns that support auditability, least privilege, deterministic calculations, and safe recommendations

### Takeaway
The strongest Penny design separates deterministic financial calculation from probabilistic explanation: bank code computes and records the numbers, while the LLM explains approved facts. Governance then covers the full lifecycle, third-party dependency, testing, transparency, and escalation—not only the prompt.

### Cited Findings
- The EBA reports that 55% of surveyed banks use GPAI or agentic AI in consumer-facing processes, including guidance, financial education, and digital assistants. It identifies third-party reliance, data quality/governance, human oversight, consent for training, meaningful explanations, hallucinations, and inappropriate or inaccurate information as key challenges. — [EBA GPAI Digital Finance Factsheet](https://www.eba.europa.eu/sites/default/files/2025-09/146b3558-d026-47bf-a872-f05e93ed30d2/Rising%2520application%2520of%2520AI%2520in%2520EU%2520banking%2520and%2520payments%2520sector.pdf)
- The EBA says GPAI's randomness and opacity create explainability limitations, that asking a model to cite sources or using RAG is not by itself sufficient for consumer-facing explainability expectations, and that GPAI requires human involvement throughout the application lifecycle. — [EBA special topic on artificial intelligence](https://www.eba.europa.eu/publications-and-media/publications/special-topic-artificial-intelligence); [EBA Risk Assessment Report, November 2024](https://www.eba.europa.eu/sites/default/files/2024-11/f03ee0c1-7258-4391-8bf1-578924956049/EBA%20Risk%20Assessment%20Report%20-%20Autumn%202024.pdf)
- The EBA's June 2026 risk report calls for risk-sensitive and transparent AI deployment, enhanced governance, stronger data/cyber security, and regular penetration testing. It also says DORA third-party oversight, ICT risk management, incident reporting, and resilience testing apply to banks' AI use. — [EBA Risk Assessment Report, June 2026](https://www.eba.europa.eu/publications-and-media/publications/risk-assessment-report-june-2026)
- DORA requires financial entities to remain responsible for compliance when using ICT third parties, integrate third-party risk into ICT risk management, document third-party arrangements, conduct pre-contract risk assessment and provider due diligence, and retain access/inspection/audit rights. — [DORA Article 28](https://eur-lex.europa.eu/legal-content/EN/TXT/?uri=CELEX%3A32022R2554)
- Under the EU AI Act, AI used to evaluate natural persons' creditworthiness or establish credit scores is listed as high-risk because it affects access to essential financial resources; a conversational budgeting coach is not automatically the same use case, but using its output for lending decisions would change the regulatory risk materially. — [EU AI Act](https://eur-lex.europa.eu/eli/reg/2024/1689)

### Inferences
- Penny should persist an audit envelope for every answer: authenticated customer/session pseudonym, tool name and version, validated parameters, data-coverage window, source account set, deterministic result, model/provider/version, safety-policy version, response, and correlation ID. Logs should exclude raw secrets and unnecessary personal content. This follows the EBA's governance/explainability concerns and OWASP's recommendation to log security-relevant tool metadata while minimising sensitive content. — [EBA GPAI Factsheet](https://www.eba.europa.eu/sites/default/files/2025-09/146b3558-d026-47bf-a872-f05e93ed30d2/Rising%2520application%2520of%2520AI%2520in%2520EU%2520banking%2520and%2520payments%2520sector.pdf); [OWASP Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/LLM_Prompt_Injection_Prevention_Cheat_Sheet.html)
- Safe-to-spend, safe-to-save, and what-if figures should be deterministic functions with visible assumptions, coverage, and confidence. The LLM should not perform arithmetic or invent missing facts; it should translate returned facts into plain language and escalate uncertainty. This is a design response to the EBA's identified hallucination and explainability risks, not a quoted EBA implementation mandate. — [EBA GPAI Factsheet](https://www.eba.europa.eu/sites/default/files/2025-09/146b3558-d026-47bf-a872-f05e93ed30d2/Rising%2520application%2520of%2520AI%2520in%2520EU%2520banking%2520and%2520payments%2520sector.pdf); [EBA special topic](https://www.eba.europa.eu/publications-and-media/publications/special-topic-artificial-intelligence)
- Recommendations should remain educational and reversible, include uncertainty and a small next step, avoid investment/credit decisions, and offer escalation or correction. Any future money movement, product sale, credit decision, or irreversible action should require separately authorised tools and fresh human confirmation. — [OWASP Prompt Injection](https://genai.owasp.org/glossary/prompt-injection/); [EU AI Act](https://eur-lex.europa.eu/eli/reg/2024/1689)

### Gaps
- EBA materials describe sector-wide risks and controls but do not prescribe a specific safe-to-spend formula, confidence threshold, or mandatory conversational wording.
- A budgeting coach's exact perimeter under Finnish consumer-protection, banking-secrecy, and financial-advice rules needs Finnish legal review; the AI Act citation only establishes the separate high-risk status of creditworthiness/credit-scoring uses.
